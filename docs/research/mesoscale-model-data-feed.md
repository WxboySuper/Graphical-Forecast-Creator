# Mesoscale model data feed research

**Checked 8 November 2026.** Scope: GFC v1.8 issues [#913](https://github.com/WxboySuper/Graphical-Forecast-Creator/issues/913), [#918](https://github.com/WxboySuper/Graphical-Forecast-Creator/issues/918), [#919](https://github.com/WxboySuper/Graphical-Forecast-Creator/issues/919), and [#921](https://github.com/WxboySuper/Graphical-Forecast-Creator/issues/921). Their shared constraint is sound: GFC presents provider parameters and does no meteorological calculation in the browser. This report is research only.

## Recommendation

Use NOAA GRIB2 as the source of truth, initially ingest a small parameter allowlist on the existing VPS, normalize to immutable cycle/hour metadata, and publish cached raster tiles plus a metadata/legend JSON endpoint through Cloudflare. Keep the ingest/provider interface independent of the hosting choice. Start with HRRR and RAP. Add RRFS after verifying the live operational inventory and run-to-publication behavior; its NCEP inventory page still calls its contents preliminary and says actual parameters may differ. Do not make Open-Meteo or SPC graphics the canonical source for a forecast workspace.

For the first “current” frame, prefer SPC Mesoanalysis when the needed field exists and the page is current, with an explicit source/time label. It is the closest available observationally adjusted analysis, though it is a severe-weather diagnostic product. Offer HRRR f00 as a separately labeled “HRRR initialization” frame, never as observations/current conditions. RAP f00 is also a model analysis and should not inherit SPC’s surface-observation adjustment. RRFS f00 has the same distinction, plus immature availability/output uncertainty.

|---|---|---|---|---|

NOAA’s NOMADS guidance explicitly recommends partial HTTP transfers for parameter/level selection and asks automated loops to include a 10-second pause. HRRR files are hundreds of megabytes in the observed listing, which makes full-file downloads on every viewer request a bad design. [NOMADS GRIB filter guidance](https://nomads.ncep.noaa.gov/info.php?page=gribfilter), [observed HRRR listing](https://nomads.ncep.noaa.gov/pub/data/nccf/com/hrrr/prod/hrrr.20260924/conus/), [NOAA NODD dataset catalog](https://www.noaa.gov/nodd/datasets), [RRFS AWS registry](https://registry.opendata.aws/noaa-rrfs/), [Open-Meteo terms/pricing](https://open-meteo.com/en/pricing).

## “Current hour” is not one thing

| Frame | What it means | Expected freshness and caveat |
|---|---|---|
| SPC Mesoanalysis | Hourly diagnostic analysis combining RAP upper-air background with surface objective analysis/observations and sounding-derived fields. | SPC guidance says products usually update by about :15 after the hour; the source page is therefore often ~15 minutes behind valid time. Surface-adjusted, but not a complete observation-only 3D analysis. Its current docs should be checked before hardcoding the old RAP description. |
| RAP f00 | RAP analysis/initial state, not a forecast made at that instant. | RAP runs hourly. A nominal f00 can be close to the cycle time, but publication and upstream data assimilation mean it is commonly tens of minutes old when available. No reliable per-cycle publish SLA was verified. It does not equal SPC’s surface-adjusted diagnostic fields. |
| HRRR f00 | HRRR analysis/initial state on the high-resolution model grid. | HRRR is hourly. One archived NOMADS listing showed 00Z f00 at 00:51Z, so f00 may be nearly an hour stale at first availability. HRRR also uses radar assimilation, but f00 is still model analysis, not a live observation mosaic. |
| RRFS f00 | RRFS initial state. | Treat as model analysis, not observed current conditions. RRFS products are newer and inventory/runtime details less settled in the published NCEP product page. A recent Unidata dissemination notice reports initial grids arriving roughly 1.5 hours after run start, with another 1.5–2 hours for full completion; this is NOAAPORT dissemination evidence and may not equal cloud-bucket latency. |

**UX decision:** label every frame with model/source, cycle time, valid time, forecast hour, and “updated/received” time where available. Use “analysis” or “initialization” for f00. Put age in minutes beside the timestamp. Suggested warning thresholds: amber after 75 minutes from valid time, stale after 120 minutes, with thresholds configurable per feed and based on `now - validTime` plus a separate delayed-publication signal. A missing newer cycle should not silently keep the old one under a “current” label. The hourly cycle cadence is enough for model frames; radar/satellite or SPC’s hourly analysis supply sub-hourly context. Do not interpolate model hours and imply new guidance. If a sub-hourly model view is desired, HRRR output includes quarter-hourly fields for its short forecast period per NCEP product documentation, but these are forecast valid times within a cycle, not new hourly analyses.

SPC methodology reference: [SPC Mesoanalysis documentation mirror describing hourly surface Barnes analysis and RAP first guess](https://www.daculaweather.com/meso_document.php) and [NOAA/NWS Mesoanalysis Think Tank report](https://vlab.noaa.gov/documents/214451/5286029/OPG%2BMesoanalysis%2BThink%2BTank%2BSummary%2BReport%2B-%2BFINAL.pdf/9107e1bd-3efd-9e88-ae2b-9eadd8be8309). The first is not an official SPC URL and may describe a prior implementation. [NCEP HRRR product inventory](https://www.nco.ncep.noaa.gov/pmb/products/hrrr/), [NCEP RAP inventory](https://www.nco.ncep.noaa.gov/pmb/products/rap/), [NCEP RRFS inventory](https://www.nco.ncep.noaa.gov/pmb/products/rrfs/), [Unidata RRFS dissemination note](https://www.unidata.ucar.edu/news/rapid-refresh-forecast-system-rrfs-and-rrfs-ensemble-forecast-system-output-availability).

## Field inventory and the no-client-calculation rule

“Native” below means a field emitted in a model’s GRIB output, not a parameter that GFC derives from other grids. Exact availability depends on product file (surface/2-D, pressure-level, native-level, or subhourly), cycle, and version. NCEP inventory pages expose per-file tables but do not provide a stable cross-model guarantee for every requested diagnostic.

| Field family | HRRR | RAP | RRFS | Practical note |
|---|---|---|---|---|
| CAPE/CIN (surface-based, mixed-layer, most-unstable variants) | Commonly available in 2-D/surface products; variant/level must be checked. | Available in selected 2-D products; verify exact layer/variant. | Likely in 2-D product but exact current inventory is preliminary. | Never collapse variants into one generic CAPE identity. Preserve parcel/layer definition and units. |
| LCL/LFC | Often emitted as diagnostic 2-D fields in selected products; not confirmed across all listed files here. | Not confirmed in every operational file. | Not confirmed from a stable published inventory. | Treat as optional provider fields until production file inventories and fixtures prove coverage. |
| 0–1/0–3 km SRH | HRRR typically exposes helicity layer fields; verify exact 0–1 km versus 0–3 km message. | RAP product output may expose helicity; exact requested layers not confirmed across all files. | Unverified in current RRFS per-file inventory. | GRIB often labels helicity as HLCY with layer encoded separately. Do not infer layer from display name. |
| Effective SRH / effective inflow layer | Not a safe cross-model native assumption. | SPC-derived diagnostics may include effective-layer values; model GRIB native presence not established. | Unverified. | Usually requires parcel-layer identification and storm-motion assumptions, so source/model-specific server derivation or a provider-supplied diagnostic is needed. |
| Bulk shear (e.g. 0–6 km) | U/V wind at levels are present; precomputed bulk shear may exist in some product variants, not confirmed across all files. | Same. | Same, preliminary. | Wind vectors are native; layer bulk shear can be derived server-side, but GFC must not do it. |
| STP, SCP, EHI | Do not assume native. Some custom/provider products may distribute them. | Same. | Same. | These are composite diagnostics, commonly calculated from CAPE/CIN, shear/helicity, LCL, and/or effective-layer inputs. Require a provider-supplied grid or separate server pipeline with named algorithm/version and provenance. |
| T, Td/humidity, wind, pressure | Core native fields in surface and/or pressure/native level products. | Core native fields. | Core native fields expected; check actual 2-D/pressure file. | Dewpoint may be explicit or require conversion from humidity. If conversion is needed, do it upstream and record it. |
| PWAT | Commonly available in selected products. | Present in selected products; confirm file inventory. | Not confirmed for every current RRFS output. | Useful contextual field; preserve kg/m² or mm convention. |
| Updraft helicity | HRRR has native maximum updraft-helicity diagnostics in selected forecast products. | Not a standard RAP convective-resolving product. | RRFS may provide it, but exact inventory/layer/period needs verification against operational files. | Definition includes layer and time aggregation. Do not compare unlike layers or accumulation windows. |

The reliable conclusion is not “all these fields exist in all three models.” It is “common thermodynamic/wind base fields exist; some diagnostics are model/product-specific; composites and effective-layer products must be discovered, not assumed.” Before implementation, download one current sample from each exact product and inspect it with ecCodes/wgrib2; save a manifest (GRIB discipline/category/number, level type/value, units, valid time, step range, grid). NCEP lists RAP f00/f02/f06 product families and the RRFS inventory warns its actual parameters may differ. [RAP sample inventory](https://www.nco.ncep.noaa.gov/pmb/products/rap/rap.t00z.wrfnatf02.grib2.shtml), [RRFS product inventory](https://www.nco.ncep.noaa.gov/pmb/products/rrfs/), [NCEP GRIB2 conventions](https://www.nco.ncep.noaa.gov/pmb/docs/grib2/). The field-level assertions above are cautious where a stable sample inventory was not found; this is a pre-implementation checklist, not a verified complete parameter matrix.

## Architecture and rough operating cost

The repo uses OpenLayers (`ol` in `package.json`, `src/maps/contracts.ts`), not MapLibre or Leaflet. It already has a Cloudflare beta Worker and a separate VPS `server/` tree. The VPS weather code currently covers TSTM generation, not a general GRIB pipeline.

| Option | Shape | Rough cost and risks |
|---|---|---|
| Cloudflare Worker + R2 | Scheduled trigger discovers cycles, fetches selected GRIB messages or upstream subset, decodes/reprojects with a suitable container/job, writes tiles/metadata to R2. Worker serves cached tiles/JSON. Keep heavy GRIB decoding out of ordinary Workers unless verified against CPU/memory/runtime limits; a container or VPS ingest can write R2. | R2 currently lists 10 GB-month, 1M Class A and 10M Class B operations free; then $0.015/GB-month, $4.50/M writes, $0.36/M reads, no internet egress fee. A 2–10 GB working/cache footprint is roughly $0–$0.15/month storage before operations; compute/Workers and upstream compute are separate. Good global delivery, but ingestion/decode is the hard part. [R2 pricing](https://developers.cloudflare.com/r2/pricing/). |
| Existing VPS ingest | Cron/systemd fetches only needed GRIB records, decodes to arrays, emits PNG/WebP tiles or Cloud Optimized GeoTIFF/JSON, then serves/cache-controls them. Could publish generated artifacts to R2 for egress-safe delivery. | Incremental direct cost is likely $0 if existing CPU/disk/bandwidth headroom is adequate; otherwise resource growth or VPS upgrade. This is the simplest operational path but competes with API/web service and needs monitoring, retries, disk cleanup, and pinned decoder versions. |
| Third-party API | Fetch API fields or pre-rendered layers and normalize metadata in a provider adapter. | Lowest initial engineering cost. Ongoing price/license and daily-call limits; free Open-Meteo is non-commercial. Risk of opaque diagnostics, provider outages, changing model mix, and terms incompatible with GFC’s public product. |

**Volume estimate:** one full HRRR native f00 file was 656 MB in a public listing; downloading every parameter/hour/cycle would multiply that rapidly. A small domain/parameter allowlist using byte ranges might be tens of MB per cycle before regridding, but that figure is an engineering estimate and varies by field count and compression. A 4-hour HRRR window at 10–30 MB/cycle is roughly 40–120 MB raw per cycle set; a domain-wide set of 15 PNG tile layers at 0.5–2 MB per layer/zoom-pyramid can reach 8–30 MB per hour if cached indiscriminately. Measure actual samples before budgeting. Use browser demand to control served tiles, not ingestion: ingest only chosen fields and retention window.

**Display strategy:** server reproject once to Web Mercator and publish XYZ PNG tiles per continuous scalar parameter, cycle, and forecast hour, with color ramp baked or values encoded in PNG/WebP plus a separate legend definition. For queryable values/alternate styling, use tiled numeric arrays/COG or vector contours. OpenLayers can consume XYZ tile URLs directly. Keep transparent nodata and avoid smoothing categorical thresholds. Generate low zoom levels from the same source grid; use per-parameter scale/legend metadata, not client meteorology.

Suggested normalized contract:

```json
{
  "model": "HRRR", "cycle": "2026-11-08T12:00:00Z", "forecastHour": 1,
  "validTime": "2026-11-08T13:00:00Z", "parameter": "most_unstable_cape",
  "level": {"type": "surface_based_parcel", "value": null, "layer": null},
  "units": "J kg-1", "source": "NOAA NCEP HRRR", "receivedAt": "...",
  "status": "current", "tileUrl": "/meso/HRRR/20261108T12/f01/mucape/{z}/{x}/{y}.png",
  "display": {"type": "raster", "palette": "mucape-v1", "min": 0, "max": 5000}
}
```

The API should return a catalog of available `(model, cycle, forecastHour, validTime, parameter, level, units)` combinations. Missing fields are omitted or marked unavailable, never substituted. Keep raw GRIB identifiers/source file and processing version in server metadata for audit and reprocessing.

## Decisions for the maintainer

1. Is “current” SPC Mesoanalysis (best available surface-adjusted diagnostic), or model f00 (explicitly called model initialization)? I recommend the former as a separate optional analysis layer and the latter as a forecast-model frame.
2. Which CONUS parameters and geographic domain are MVP? Every added field expands ingest, validation, cache, legend, and stale-state work.
3. Is a GFC-operated server-side pipeline an acceptable “provider” under #918? I recommend yes, with versioned documented formulas only for fields the provider cannot supply, never calculations in the client.
4. Should RRFS be in v1.8 launch scope, given preliminary output documentation and late completion? I recommend a feature flag / later provider addition.
5. Is an hourly model frame with radar/SPC sub-hourly context sufficient, or does MVP require HRRR 15-minute forecast frames?
6. Who owns feed health and updates when NOAA changes product inventories, terms, or distribution paths?

## What I could not verify

- I did not find a current official NOAA WMS/ArcGIS endpoint that exposes the required HRRR/RAP/RRFS grids with reliable freshness and browser CORS guarantees.
- I did not verify CORS headers on each cloud bucket/API endpoint; implement through a GFC origin regardless.
- I did not find a published NOMADS hard request quota or SLA. Its documented 10-second loop guidance is the usable limit signal.
- I did not produce a complete message-by-message inventory for current HRRR, RAP, and RRFS sample files. In particular, RRFS and effective-layer/composite availability need live file inspection.
- Cloud mirror lag and per-cycle RAP/RRFS f00 publication age vary; the HRRR 00Z listing is a single observed example, not a service guarantee.
- Approximate per-cycle subsets and tile sizes are planning estimates, not measured GFC artifacts.
